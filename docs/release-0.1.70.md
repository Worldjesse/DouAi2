# 0.1.70：独立评论回复

本地构建版本 `0.1.70 / 71`，目标宿主为抖音 `40.6.0 / 400601`。本次实现「自动回复 → 评论回复」，使用已经配置的 AI 模型回复别人对本人评论的新回复。默认关闭，独立于私信/群聊回复和刷作品自动评论；受自动化总开关控制，“立即停止”会同时关闭它。

本文保留首版本地实现记录；后续 [0.1.71](release-0.1.71.md) 已将评论回复并入父自动回复，共用模式、提示词、额度与历史，当前行为以新版记录为准。

本文记录本地实现与验证，不表示已发布到 GitHub 或 LSPosed。此前的接口探寻与 APK 证据见 [分析报告](2026-10-17_reverse-douyin-comment-reply-report.md)。

## 使用

1. 在模型配置中添加并启用模型。
2. 打开「自动回复 → 评论回复 → 开启评论回复」。首次开启只建立当前账号的消息起点，不追发已有旧消息。
3. 后续使用抖音时，收到评论内推会触发增量扫描；前台另有低频补扫，冷启动和真正从后台返回时也扫描一次。
4. 从「评论回复记录」查看本功能的输入、正文、对象和发送状态。可开启发送前提示，在提交前长按取消。

首版只处理能够核实“对方引用本人评论”的文本回复。不会把自己的评论、单纯提及、别人作品下无关讨论、身份或线程不完整的通知当作回复目标。AI 输入包含作品说明、自己的原评论和对方回复，采用独立二级提示词，不混用私信或作品自动评论上下文。

默认每日最多 20 次，同一用户间隔 1 分钟，同一评论线程最多 3 次；每日数和用户间隔的 0 表示不限，线程次数可设 1 至 100。账号之间的消息起点、任务、去重和额度隔离。

## 接收与回复链路

- 复用宿主现成 notice Retrofit 实例，显式 `is_mark_read=0`，不调用会固定标已读的旧包装器。
- 遵循宿主的 `max_time/min_time` 双游标，分页请求保持游标原值；比较时间按宿主约定兼容秒与毫秒。失败、取消、响应异常、游标循环或超过分页上限均不推进处理水位。
- 首次基线收齐同一秒跨页的已有评论 ID，允许该秒之后到达的新 ID 被处理。后续保留五分钟重叠，并按账号加真实评论 ID 持久去重。
- 应用内推只发出扫描信号，发送目标始终取已核验的通知模型；不会使用当前正在刷的视频代替通知中的目标作品。
- 发送使用宿主权限检查后的原生 `CommentPublishRequest`，把被回复模型写入 `0yFs.p`，由宿主生成回复定位参数。回包需同时匹配作品、根评论及楼中楼目标才标为成功。

暂不依赖通知是否已读。服务端拒绝、删除或不可见、缺失身份/正文/线程字段的消息不会盲目发布。缺字段会记录诊断；本次静态资料不能证明真实消息的字段完整率。

## 任务与发送状态

任务在 AI 生成前同步保存占位；进入宿主发送前同步保存 `submitted`，写入失败就禁止发送。前台中断、切账号、配置变化、额度暂不可用及预览队列满会暂缓未提交任务，不消耗失败次数。手动取消为终态；明确生成或发送失败最多尝试三次，间隔至少一分钟。

已提交但超时或结果未知的请求保留去重，不自动重发；迟到的明确结果可以更新记录。进程重建只恢复尚未越过提交边界的占位，已提交和未知结果继续保留。记录容量上限为 10000 个评论 ID，满后停止授权新任务，不淘汰未知请求。

离开前台会立即阻止新的发送，确认进入后台后取消生成；已提交请求继续收结果。Activity 内切页不作为每次打开重新全扫。扫描跨后台恢复或切号时，会在旧请求退出后补排新扫描，避免等待下一次定时检查。
