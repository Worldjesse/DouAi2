# DouAi 0.2.1 本地诊断与交互调整

版本 **0.2.1 / 102**，宿主取证范围为抖音 **40.6.0 / 400601**。本轮优先定位语音发送成功率低的原因；减少等待是次要调整。最终签名归档已完成严格本地验收，尚未远端提交或发布。本版产物与证据列于下文，[0.1.100](release-0.1.100.md) 的结果保留为历史记录。

本版采用[版本进位规则](releasing.md#版本进位规则)：末段满 100 向中段进位，中段满 10 向首段进位；本次草稿号 `0.1.101` 规范化为 `0.2.1`，versionCode 保持独立递增。

## 使用变化

- MiniMax 主页面保留“模型”和“音色”入口，移除分散的刷新行。模型列表内点“刷新”，再选择“当前接口模型（使用 API Key）”或“MiniMax 官方目录（无需 Key）”；音色列表内直接刷新账户音色。两种列表均保留手动填写。打开缓存、内置或空列表不自动联网，更不会触发收费合成；只有选择具体刷新操作才请求目录。
- Miuix 普通表单、提示词与聊天输入共用局部文本编辑桥，避免每输入一个字符就重写隐藏 `EditText` 的全文；过滤后的光标与组合范围按实际接受的文本映射，聊天中间编辑不再强制光标跳到末尾。可见输入回归覆盖长文本局部插删、中间插入保留原后缀、满长度拒插、完整 emoji 替换和草稿取消不保存。聊天仅编辑草稿时保留现有历史，同一 4 行记录测试中的历史 `getView` 次数从 4 降为 0；发送、重试和附件等其他刷新仍走完整路径。这些操作次数与正确性结果不能代替实际手机卡顿或真实输入法验收。
- 自动评论与自动回复的悬浮预览，在尚未保存提示超时时默认 **3 秒**；运行时与编辑页引用同一默认值。已经保存的 8 秒或其他值不被改写，取消与立即发送仍可用。这只减少默认预览等待，不承诺整个生成、上传或回执在 3 秒内完成，也不改用户的 AI 推理强度。
- 不把宿主录音界面的 30 秒配置当成上传上限。自动评论与评论回复语音不据此新增模块时长硬限制，不截断正文或音频，也不为迎合该录音默认值而自动加速或额外合成。评论回复调用方原有的 30 秒模块限制也已移除。私聊、群聊语音的 120 秒限制与录音文件替换入口的 30 秒限制仍分别保留；服务接口、音频有效性、原有失败重试/回退及未知结果防重继续生效。
- 宿主评论回执补读继承的数值 `errorCode`，并为本模块持有的语音任务增加受控 `audio_phase`，区分上传/鉴权阶段、取得上传结果后的发布阶段及无法判定的阶段。本轮还补充 `audio_receipt=present|missing|unknown`，单独观察音频回执结构是否具备非空标识和正时长，不改变原有 ACK 判定；最终 APK 中的诊断锚点已静态核对。不记录音频标识、路径、正文或服务端原始错误内容。语音准备失败补充 MiniMax 的 `providerCode` 和 HTTP 的 `httpCode`；抖音宿主回执的 `code` 属于另一错误码体系，不能套用 MiniMax 错误表解释。旧日志缺少这些字段，仍须新版设备日志才能定位实际失败原因。
- 评论回复增加“我的评论”窗口短期复用：有效缓存仍读取一页新鲜头页和新的线程内容，账号、任务有效性和反证撤销继续优先。新增 `own_ms`、`thread_ms`、`lookup_ms` 与缓存来源，便于区分回源、线程查找和生成等待。实际手机提速尚未验证。
- 备份失败按读文件、UTF-8 解码、格式/配置校验和应用配置等阶段诊断。用户提供的 **22,559 字节**备份在本地 SDK 35 / Robolectric 4.14.1 环境下可预览：**97 项配置、2 条分析数据**，合并与覆盖两种模式均通过。该结果不能证明 Android 16 实际手机上的报错已复现或修复。如再次失败，可先反馈新版界面显示的分阶段提示原文，无需上传密钥或完整 JSON；`DouAi` 标签的备份阶段、异常类型及读取摘要写入 Logcat，LSPosed 导出是否包含它们取决于采集范围。

具体操作见 [使用帮助](help.md#minimax-模型列表)，证据、样本统计和未解决问题见 [2026-10-20 诊断记录](diagnostics-2026-10-20.md)。

## 证据边界

0.1.100 日志中，5 份音频各发生 3 次明确失败，共 15 次语音提交失败，随后 5 次完整文本回退成功；0.1.99 则有 22 次语音提交，20 次失败、1 次被旧模块判为 `sent`、1 次缺少回执。唯一 `sent` 所用音频长 28.260 秒；旧判定只核对状态码、评论 CID 和作品 AID 等 ACK 条件，没有检查 `response.comment.commentAudio`，也没有验证评论实际携带音频或可播放。时长、大小、作品权限及服务端条件没有被独立控制，不能由此认定存在 30 秒或某个文件大小的上传阈值。

宿主录音路径与模块路径在编码、容器和波形上存在差异。上述单条 `sent` 回执不足以排除 MP3 或空 `wave` 对失败的影响；这些差异与失败之间的因果关系仍未知。新增 `audio_receipt` 在宿主 `chain.proceed()` 后投递主线程读取回调对象，未抓取原始 HTTP 响应，也不保证对象未经宿主处理修改。`present` 仅说明观察时具备相应音频元数据，不能证明服务端媒体校验通过或音频可播放；`missing` 或 `unknown` 也不改写现有 ACK 语义。

原始 APK 的 22 个类已直接从 DEX 复核：30 秒位于录音设置；跟踪到的 Java 上传/发布支路未发现对应硬比较。native 上传 SDK 与服务端规则不在已验证范围内。“未发现 Java 检查”也不代表服务器无上限。

回执与发布模型另有独立的 6 类静态复核，保存在 `work/comment-voice-verify-20261020/response-review/`，各类摘要见 `class-hashes.json`。该补充范围不改写或替代原 22 类核验，具体证据边界见诊断记录。

MiniMax 国际公开文档的 T2A 表列出部分 Speech 模型 **60 RPM**，并说明限制依模型与接口而异。这不是对所有中国区账户、代理地址或自定义服务的额度承诺。本次相关音频已完成准备并进入宿主发送流程，旧版 HTTP 402 记录不能混作本轮宿主失败原因。依据：[速率限制](https://platform.minimax.io/docs/guides/rate-limits)、[错误码](https://platform.minimax.io/docs/api-reference/errorcode)。
