## 结论

选择视频后出现多张缩略图和一个文件名，符合当前“视频抽样帧 + 视频说明”的输入实现，并不是把文件名错当图片。大 X 和一横排多个项来自发送前预览的布局：每帧各生成图片项和 48 dp 删除按钮，随后再为同一个视频生成说明项和另一个删除按钮。这种展示没有清楚表达“它们属于同一段视频”，应改进预览交互。

等待也有实际日志证据。抖音 PID 26224 的同一后台线程 19516 出现两批各四次 `MediaMetadataRetriever` 慢 Binder 调用，每批已记录的调用耗时累计约 24 秒，与源码顺序读取至多四帧、完成后一次加入草稿的路径吻合。没有证据把该现象定为文件损坏、FFmpeg 失败或图像读取异常。

截图仍显示发送前附件草稿；图中没有这次视频对应的已发送消息或模型错误提示。日志也没有本次聊天视觉请求的明确成功/失败记录。存在的 HTTP 402 属于自动评论的 `stage=synthesis`，不能作为该视频视觉请求失败的证据。

## 代码如何生成这一排草稿

快照 `ChatMediaLoader.java:62` 的统一入口按 IMAGE / VIDEO / DOCUMENT 路由。视频会先复制到私有缓存，限制 64 MB，然后 `loadVideoDocumentFile`：

1. `:112` 使用 `MediaMetadataRetriever.setDataSource`，读取时长和尺寸；最长边限制 1280。
2. `:128` 按 `sampleTimes` 生成抽样时间。数量最多为剩余图片预算（每消息总计最多 4 张图片或视频帧），同时不超过按秒计算的时长数量。
3. `:129` 顺序调用 `getScaledFrameAtTime(..., OPTION_CLOSEST_SYNC, ...)`；每帧 JPEG 85 编码。目标为关键帧附近，可能得到重复画面。
4. `:138` 返回一个含文件名、抽样说明和帧列表的 Document。说明明确它只包含抽样画面，不包含音频、语音或其余片段。

`AiTestChatDialog.java:878` 在后台单线程 worker 读取附件，UI 显示“正在读取附件…”，`loadingImage` 阻止此时发送。只有读取整体完成后，`:892` 的主线程回调才把媒体加入草稿，因此当前没有逐帧可见进度。

`addAttachment:926` 同时保存 `Document(name,text,images)` 与 `draftImages`。随后 `renderAttachments:948` 分两轮创建视图：

| 轮次 | 视图 | 截图结果 |
|---|---|---|
| 每个 `draftImages` 帧 | 64×56 dp 预览 + `square()` 的 48×48 dp 删除按钮 | 同一视频变成多张横排缩略图，每帧带大 X |
| 每个 `draftDocuments` | 最多两行、最大宽 160 dp 的文件名 + 48×48 dp 删除按钮 | 同一视频又出现一个文件名和大 X |

这是 UI 将一个逻辑附件展开为多个预览项，不是一次选择了多个文件。文件名和媒体内容仍由 Document 中的帧列表关联。

## 删除、取消与资源问题

删除分组当前是正确关联的：图片 X 在 `:957` 查找包含该帧的 Document，若存在则删除整个视频/PDF 的帧组和说明；文件 X 在 `:976` 同样删除说明及其全部关联帧。没有发现“只删了说明但继续发送同视频剩余帧”的确定逻辑错误。但视觉上每帧一个 X 容易让用户误以为只删该帧，实际却删整个视频，应改为单个逻辑附件卡片的删除入口。

取消已具备晚结果防护：`cancelImageLoad:1036` 取消 Future、递增 `imageGeneration`，主线程回调通过 generation / disposed 检查拒绝过时结果。然而聊天 `loadVideoDocument` 传入的 `MediaReadCancellation` 为 null，依靠线程 interrupt 在调用之间检查；同步的媒体 Binder 调用内部没有该代码可触发的强制中断或截止时间。取消后，正在进行的调用返回前仍会占用 worker。附件读取与聊天请求共用单线程 worker，因此不能把 UI 取消理解为原生解码已经立即停止。自动评论另有 `MediaReadCancellation` 不代表这条聊天路径已经使用它。

还发现一个独立的缓存积累风险：移除草稿附件只删 draft 列表，未从 `thumbnails:IdentityHashMap<ChatImage,Bitmap>` 删除已经生成的缓存项。缓存键继续持有 ChatImage 的 base64 数据，直到清空聊天或关窗才整体清掉；反复添加、删除附件可能积累内存。新异步结果会由 `retains(image)` 拒绝，但已缓存结果没有同样的逐附件清理。本次日志没有相应 OOM，不能把该风险写成本次等待的已发生根因。

## 模型视觉能力与请求证据

静态发送协议会把视频帧作为图像输入：`ChatCompletionClient.java:461` 之后分别构造 Chat Completions 的 `image_url`、Responses 的 `input_image`、Anthropic 的 base64 image 或 Gemini inline_data，并把抽样说明和图片序号一起交给模型。原视频文件和音轨不会按完整视频直接上传。

该协议构造能力不证明用户选择的具体模型接受图像。截图联系人名不能作为实际 API 模型身份或能力的证据。当前日志没有记录这次聊天请求的协议、HTTP 状态或拒绝原因；正常聊天异常主要显示在对话 UI，不一定进入 LSPosed 模块日志。故本包不能确认这次视觉请求成功，也不能确认它被模型拒绝。

在新模块日志 `log/modules_2026-10-18T11:35:53.473382.log:207/209/211`，11:36:05.091、11:36:06.683、11:36:10.009 有自动评论 `stage=synthesis; reason=http_402`。这些是其他功能的语音合成失败，发生在两次文档选择器之前，不用来解释 11:36:31 之后的视频草稿读取。

后续实现采用 `0.1.79 / versionCode 80`，按下面的用户流程调整。该节对应当前源码，前面的日志与行号仍对应保全的旧实现快照；本地验证和真机验证分别记录。

1. 消息页聊天的图片和视频使用抖音原生选择器，文件继续使用系统文档选择器。原生选择结果交回模块，不进入抖音好友会话的发送链路。
