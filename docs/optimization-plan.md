# DouAi 优化实施计划

制定日期：2026-10-12。基线版本：0.1.46 / versionCode 47。状态：分阶段实施中。

目标是提高异常恢复能力、减少运行时重复工作，并降低抖音升级和新增设置的维护成本。按阶段分批交付，每批通过对应验收后再推进。已完成本地验证基线、异常恢复及性能改动，并实施媒体取消、宿主适配诊断、模型编辑器和互动自动化弹窗拆分。用户反馈 R8 试验包测试无问题，正式 Release 已采用同一压缩配置；其他功能的设备行为与性能验收仍分别记录。

## 范围与基线

- 保留正式包名、发布签名、libxposed API 102 和现有功能默认值。
- 保留唯一候选判定、Hook 回滚、账号隔离、任务去重，以及提交和确认成功的区别。
- 当前已验证宿主为抖音 40.6.0；支持其他版本需要独立验证。
- [现有发布记录](releasing.md) 记载 591 项测试通过、Release Lint 0 错误和 41 警告、APK 25,390,227 字节。这些是既有结果，实施时需要重新建立基线。
- 真机功能、网络发送和性能结果应单独记录；扫描成功和 Hook 安装成功不能作为实际功能成功的证明。

## 阶段 0：建立验证基线

1. 重新运行当前测试、Release Lint 和构建，记录失败、跳过项、现有警告和产物大小。
2. 增加普通 CI 检查，使用项目要求的 JDK 21、Android SDK Platform 37 和 Gradle Wrapper。
3. 将宿主 DEX 测试与普通测试分开报告。普通 CI 未提供 APK 时明确标注该测试未执行；适配发布检查必须提供合法取得的本地 APK 并确认测试通过。
4. 整理真机验收场景：冷启动、连续切换作品、组件隐藏与恢复、设置即时生效、账号切换、前后台切换和发送确认。
5. 在同一设备、宿主版本和功能配置下测量冷扫描与缓存启动耗时、P95 帧耗时、GC/内存变化、历史页打开耗时。先形成基线，再确定性能目标。

**验收：** JDK 21、Android SDK Platform 37 下完整运行 619 项测试，0 失败、0 跳过；包括本地抖音 40.6.0 全 DEX 规则测试。Release Lint 为 0 错误、44 警告；Release 构建成功。新增 [Android CI](../.github/workflows/android-ci.yml) 使用 JDK 21 和 Android SDK 37；没有配置宿主 APK 的 CI 运行会明确报告宿主扫描未验证。真机及性能基线尚未完成。

## 阶段 1：修复异常恢复

### 批次 1：缓存保存失败降级

入口：[HostScanner.java](../app/src/main/java/com/douai/module/scan/HostScanner.java)、[DouAiModule.java](../app/src/main/java/com/douai/module/DouAiModule.java)。

- 将扫描结果与缓存持久化结果分开处理，缓存保存失败仍返回有效扫描报告。
- 单独报告缓存故障；真正的 DEX、规则解析或扫描错误仍按原有失败语义处理。

**验收：** 使用确定会保存失败的缓存目标，完整报告仍可供后续 Hook 安装使用；缓存正常命中不重新扫描；下次没有有效缓存时能重新扫描。扩展 `HostScannerTest` 和 `StartupHostCacheTest`。

### 批次 2：评论队列统一拥有任务

入口：[AutoCommentQueue.java](../app/src/main/java/com/douai/module/feature/AutoCommentQueue.java)、[AutoCommentHook.java](../app/src/main/java/com/douai/module/feature/AutoCommentHook.java)。

- 由队列统一管理接纳、拒绝、查询和取消，或在异步接纳后回调登记任务。
- 让取消最新项、队列计数和任务释放使用同一份实际队列状态。
- 保留现有去重、账号隔离、重试次数及已提交任务的处理方式。

**验收：** 取消或失败作品再次出现时无残留任务；再次取消最新项能命中实际排队任务；重复接纳、队列满、reset、close、迟到回调都不会使任务记录与队列失配。扩展 `AutoCommentQueueTest` 和 `AutoCommentHookTest`。

### 批次 3：续火花发送状态与恢复

入口：[NativeMessagingHooks.java](../app/src/main/java/com/douai/module/feature/NativeMessagingHooks.java)。

- 定义带时间戳和 attempt token 的发送记录，区分发送中、已确认成功、已确认失败和结果未知。
- 发送前在后台确认必要记录已持久化；持久化失败时终止本次发送并报告原因。
- 处理同步异常、回调缺失、重复回调、迟到回调和进程重启。调用发送接口后发生异常或超时，按结果未知处理。
- 将旧版布尔 `pending` 迁移为结果未知。能从宿主记录确认结果时更新状态；无法确认时展示状态并提供明确的重试入口。
- 保持已确认成功的当日抑制；自动重试只适用于已确定未提交或明确失败的任务。

**验收：** 在持久化后、调用发送时、等待回调时模拟异常或重启；成功状态不重复发送，结果未知不自动重发，旧回调不覆盖新的 attempt。扩展 `NativeMessagingHooksTest`。

**已完成：** 添加带时间戳和 attempt token 的发送账本；旧 `.pending` 与重启遗留的发送中记录迁移为结果未知；发送前同步落盘；30 秒无回调时转为未知；未知结果必须在 UI 明确确认后才能重试。账本测试覆盖提交失败、迁移、进程恢复、回调超时、重复及迟到回调、重试 token 和 reset。

### 批次 4：覆盖媒体阶段的取消与截止时间

入口：`AutoCommentHook`、`AutomationImages`、`AutomationCommentMedia`、`MediaStoreDownloader`。

- 将任务取消覆盖媒体下载、采帧和 AI 请求，持有必要的 Future/连接，并设置整个操作的截止时间。
- 给媒体保存增加等待队列上限、进行中任务去重和完成通知，保留字节上限及失败清理。

**验收：** 慢速媒体传输中取消后，连接被释放，下一任务可以启动；重复点击不重复提交同一媒体；队列满有明确结果；失败不残留不完整的 MediaStore 记录。

**已完成：** 媒体保存线程池等待队列限制为 16 项，按媒体 URL、文件名和目标集合去重；重复任务或队列满会提示用户。评论每次生成持有独立的取消状态和提交前创建的 FutureTask；用户取消、配置重置、关闭和超时会中断对应任务、断开活动媒体/AI 连接。媒体阶段使用 60 秒的共享截止时间，生成阶段使用 120 秒整体截止时间；超时主动完成一次队列结果，迟到结果不能写入文本或进入发布，重试使用新的取消状态。

**本地回归：** 阻塞图片响应头/正文取消、部分视频临时文件删除、取消后下一作品生成、禁用期间取消、任务尚未启动的超时和 AI 超时重试均有覆盖。图片解码与视频采帧在调用边界检查取消并释放 Bitmap/文件；Android 原生解码的单次调用无法强制打断，若 native 调用卡住，逻辑队列可超时，但不能保证唯一工作线程立即释放。

## 阶段 2：减少重复工作

### 批次 5：配置差异分发

入口：[DouAiModule.java](../app/src/main/java/com/douai/module/DouAiModule.java)、`FeatureSettings`、`ExtendedSettings`、`LocalOptions`。

- 完整读取一份一致的配置快照后再发布，读取失败保留上次完整状态。
- 合并同一轮多键通知，按各功能相关配置是否变化进行更新。
- 首次安装 Hook 全量初始化；模型、账号和自动化范围变化仍使旧任务失效。

**验收：** 修改 AI 提示词不会重新应用播放器和组件隐藏；相同值不会触发重复更新；组件设置即时生效；批量保存、`clear()` 和读取失败不会出现新旧配置混用。

### 批次 6：缓存 Feed 隐藏目标

入口：[FeedUiHideHook.java](../app/src/main/java/com/douai/module/feature/FeedUiHideHook.java)。

- 分开目标发现与样式维护，在绑定、重绑、结构或配置变化时重新定位。
- 每帧仅检查缓存目标。为异步插入和未解析定位器提供有界重试；覆盖复用 View 的 ID、描述和内容变化。
- detach、close、暂停和恢复时正确移除监听、释放引用并恢复原状态。

**验收：** 稳定视图连续绘制不触发全量发现；宿主重置 alpha/visibility 后仍能及时恢复效果；卡片切换、异步插入、重绑、自定义定位和暂停恢复均通过现有回归。随后用阶段 0 的真机场景比较帧耗时与内存。

**已完成：** 卡片与窗口的绘制回调只重用已缓存目标；自定义定位失败后重试次数有上限；新增连续绘制回归与视图查找计数。异步层级变化和实际帧耗时仍待真机确认。

### 批次 7：历史列表与对话后台加载

入口：[AutomationHistoryDialog.java](../app/src/main/java/com/douai/module/ui/AutomationHistoryDialog.java)、`AiTestChatDialog`。

- 将历史读取、JSON 解析和图片恢复移到后台。
- 历史列表使用单个 Compose `LazyColumn` 或 RecyclerView，仅创建可见行。
- 页面关闭时取消加载，并防止旧请求回写已关闭或已清空的页面。

**验收：** 空记录、每类 200 条历史、含图片的对话均可正常打开；详情、清空和关闭行为保持；主线程不读取完整历史或解码全部图片。

**已完成：** 自动化历史使用后台读写及虚拟 ListView；测试对话在后台恢复消息并解码图片缩略图，关闭、发送及清空会使旧恢复结果失效。普通 UI 与 Miuix 虚拟列表均通过当前回归。

规则索引与反射成员缓存作为测量后的候选优化：仅在冷扫描或反射耗时确实突出时实施，并验证扫描报告等价性。

## 阶段 3：集中宿主适配

入口：`HostRuleSet`、`HostTargets`、`douyin-host-rules.tsv`，以及使用数字资源 ID 的功能。

1. 建立宿主适配配置，将版本/已验证标识、方法规则、字段访问和资源映射集中管理。
2. 先迁移当前 40.6.0 配置；新增版本单独提供验证结果。
3. 为资源匹配增加资源名、控件类型或父容器角色验证，按实际可用证据选择条件。
4. 按功能显示缺失规则、资源不符或未验证状态，关闭受影响能力，保留已验证可用能力。
5. 将适配信息用于诊断，明确区分规则命中、Hook 安装、功能启用、运行触发和实际成功。

**验收：** 40.6.0 全 DEX 规则仍唯一匹配；资源不符和模拟未知版本不会操作错误控件；诊断能指出具体受影响功能。方法扫描通过后仍需要真机确认资源与实际行为。

**已完成首批：** `HostAdaptation` 集中本地 APK 实测包名 `com.ss.android.ugc.aweme`、版本 `40.6.0`、versionCode `400601`、规则资产指纹与 47 项 Feed 资源名。文件名中的其他数字不作为 versionCode。原始版本通过 sourceDir 的 APK 清单解析读取，避免版本伪装污染诊断。

`HostFeatureCatalog` 与 `HostAdaptationDiagnostics` 集中首批 20 项主要能力的必需规则和安装标志；报告具体缺失/歧义规则、视频/图文部分安装、资源不符及未验证版本。版本和规则配置符合静态证据不代表本次扫描或实际行为成功。两个运行时可撤销的计数/撤回背景 Hook 诊断读取实际注册状态。

Feed 组件、自动关注和手势评论入口的数字 ID 操作均需包名和资源名一致；不符时跳过目标或走原有非数字定位路径。复杂替代规则、字段访问和扩展能力尚未全部集中；自动关注及手势入口的资源不符没有独立累计诊断，保持安全跳过。

## 阶段 4：整理设置与控制逻辑

入口：[ModuleSettingsScreen.java](../app/src/main/java/com/douai/module/ui/ModuleSettingsScreen.java)、`DouAiModule`、`MainActivity`。

1. 沿现有独立设置页面模式，依次抽出 AI 模型和自动化页面，统一弹窗生命周期与可取消请求。
2. 在设置所属模块集中定义 key、默认值、解析、范围和展示规则，先修复倍速输入与生效值不一致。
3. 集中管理功能安装结果与诊断状态，使模块入口和状态页使用同一份功能信息。
4. 每次仅迁移一组职责，保留现有设置 key、迁移逻辑、配置隔离和热更新行为。

**验收：** 倍速 `0.25`、`4` 可保存，越界值、非数字和非有限值显示校验结果；预览与生效值一致。旧配置升级保留值；模型编辑器关闭能取消请求；现有设置、Compose 与生命周期测试继续通过。

**已完成：** 倍速编辑器使用小数输入并拒绝 `0.25` 至 `4` 之外的值；旧配置无效时预览与运行时默认值一致。`AiModelEditor` 独立管理草稿、校验、保存/删除、子弹窗、测试对话和模型列表请求；关闭、保存、删除及父页面关闭会断开连接并取消 Future，迟到响应不能更新旧界面。

`AutomationSettingsDialog` 独立管理互动自动化开关、立即停止和关闭；每次编辑读取最新完整设置，保留其他功能值，关闭后旧控件不能继续写入。主设置页负责导航、对话框登记和列表刷新，保留既有配置 key 与 Miuix/普通 UI。自动回复/评论的复杂范围页面仍在主设置页，后续按实际维护需求整理。

## 阶段 5：优化包体积并验证发布

1. 使用独立试验构建启用 R8，先保持必要类名，明确保护 Xposed 入口、反射访问和宿主 Compose 集成。
2. 对比未压缩与压缩产物大小、启动表现和实际功能，检查模块元数据是否完整。
3. 再评估资源裁剪；只有通过资源加载和真机回归后才用于正式版。
4. 按 [发布流程](releasing.md) 验证包名、版本、签名、摘要和安装升级，并更新实际验证结果。

**验收：** 压缩产物在目标宿主中完成扫描、注入、设置页加载和关键功能验证；包体积收益有实测数据；不能通过时保留原构建方式及试验记录。

**试验及正式采用：** 首轮 `r8Experiment` 保留模块类/成员及 ActivityResult 宿主反射契约，不裁剪资源。APK 契约测试捕获 ActivityResult 类名被 R8 改写的问题，补充保留规则后重建。用户于 2026-10-12 反馈“r8 我测试了，没问题”，正式 Release 随后采用同一配置；`r8Experiment` 继承 Release，保留兼容构建入口。

用户反馈作为 R8 使用测试通过的记录，具体设备、宿主版本与覆盖场景未提供，不推定实际发送或性能测量已完成。正式 mapping、configuration、seeds 和 usage 位于 `app/build/outputs/mapping/release/`。`ApkArtifactContractTest` 直接检查正式 APK 的 Xposed 元数据、源码规则资产、入口签名、宿主反射名称与 opcode 文本，以及 compileOnly API 不被打包；签名、Manifest 和大小另外检查。

## 每批交付要求

- 一个明确的行为改动、一组覆盖失败路径的回归，以及对应验证结果。
- 窄范围修改先运行对应测试；涉及共享配置、状态契约或发布构建时运行全量测试和 Lint。
- 结构调整和新行为尽量分开提交；状态迁移先验证旧数据读取及升级恢复。
- 真机结果记录“已验证 / 未验证 / 失败”；实际发送成功需要宿主回调或记录证据。
- 日志和报告不包含 API key、完整私聊内容或发布密钥；第三方 APK 不加入公共仓库。

在配置好 `ANDROID_HOME` 和 JDK 21 后，全量检查命令为：

